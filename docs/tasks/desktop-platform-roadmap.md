# 桌面端开发计划

> 状态：方向已确认，尚未开始实现。
>
> **长期目标是 Tauri**：后续会逐步学习 Rust，并在能力和兼容性验证充分后将 Tauri 发展为桌面端实现。
>
> **近期先交付 Electron**：它复用当前 TypeScript 技术栈，避免 Rust 学习节奏阻塞第一版可用桌面应用。Electron 不是与 Tauri 竞争的长期产品线，而是先行交付与产品规则验证线。

本文是桌面端相关工作的唯一计划源。两条线共享产品规则，但不并行重复实现完整功能。

## 1. 已确认的产品边界

- 应用将保留并扩展“本地优先”的能力：用户可绑定自己合法拥有的本地音频文件。
- 后端将发布版本化的默认专辑、歌曲和单曲元数据；用户可新增、修改、隐藏或排序自己的目录内容。
- 默认 Bilibili 来源仅保存结构化视频引用，例如 `bvid` 与分 P；后端不保存、缓存、代理或分发音频流、临时播放 URL、Cookie 或用户凭据。
- Bilibili 实际播放与用户登录态仅在用户自己的桌面客户端内处理。来源不可用、受地区/会员限制或下架时，必须明确提示并允许改用本地文件或用户自定义来源。
- 默认来源必须有可审查的来源记录、核验时间和状态。不得把未经核验的搬运、翻唱、混剪或 Live 视频表述为默认正式音源。
- 不得绕过登录、会员、地区或 DRM 限制；不得提交音频、歌词、封面、Cookie、抓取快照或播放 URL 到仓库。

在开始任何 Bilibili 播放相关实现前，必须把上述范围同步到项目的版权与架构文档，并完成对拟采用依赖及许可证的审查。

## 2. Git 分支、职责与计划同步

```text
main
├─ desktop/electron    Electron 产品交付主线
└─ desktop/tauri       Tauri 长期目标与 Rust 学习验证线
```

| 分支 | 定位 | 成功标准 | 禁止事项 |
| --- | --- | --- | --- |
| `main` | 稳定集成线与计划唯一来源 | 保持已验证的 Web MVP、公共领域规则和开发计划 | 不直接混入未验证的桌面端试验代码 |
| `desktop/electron` | 近期产品交付线 | 能安全打包、运行当前应用，并逐步支持桌面适配能力 | 不把用户凭据或音频流发往后端；不为未来 Tauri 提前大规模重构 |
| `desktop/tauri` | 长期目标的学习与验证线 | 验证现有 React/Vite 前端、本地音频与受控 Rust 调用在目标系统可用 | 在 Electron 验证同类产品规则前，不重复实现完整歌单、目录、Bilibili 来源或后端功能 |

并行开发时使用独立 Git worktree，避免依赖目录、构建产物和开发服务器相互干扰。

### 计划同步规则

1. 计划、架构边界或产品决策先更新本文并提交到 `main`；它是所有分支应遵循的唯一来源。
2. 开始某个桌面端任务前，先将 `main` 的最新计划合并或变基到目标分支，再检查该任务的前置条件。
3. 每个桌面端提交只实现当前计划中的一个任务；提交说明写明所属阶段，例如 `desktop(electron): complete shell baseline`。
4. 发现平台差异、阻断或新的安全风险时，不在分支中临时改变目标；先回写本文的“决策与风险”记录，再继续实现。
5. 平台无关的领域规则与测试先回到 `main`，桌面端分支只保留各自的适配层。这样 Tauri 后续可复用已验证的 TypeScript 规则。

若未来决策、取舍或外部约束变多，再新增 `docs/decisions/` 下的独立决策记录；当前不需要为每个分支各维护一份重复计划。

## 3. 分层规则

下列领域规则应继续保持平台无关，并优先留在现有 TypeScript 业务层：

- 专辑、歌曲、队列项、播放快照和歌单规则；
- 默认目录与用户覆盖层的合并规则；
- 来源优先级和可用状态的纯规则；
- 元数据校验、目录版本合并与迁移规则。

各桌面端仅负责平台适配：

| 能力 | Electron | Tauri |
| --- | --- | --- |
| 窗口、打包、自动更新 | 主进程适配 | Rust 运行时适配 |
| 本地文件与安全存储 | 受控 IPC | 受控 Tauri command / 插件 |
| 用户本机播放来源 | 主进程与渲染进程的受控协作 | Rust command 与 WebView 的受控协作 |
| 后端目录 API | 共享 TypeScript 客户端 | 共享 TypeScript 客户端 |

渲染层不得直接获得 Node、Rust 原生能力或用户敏感凭据；只暴露最小的、显式定义的调用接口。

## 4. 后端目标架构

后端第一阶段只负责元数据与用户覆盖，不参与媒体代理。

```text
Catalog API
├─ 发布默认目录版本
├─ 发布已核验的来源候选引用
├─ 保存审核、来源和回滚记录
└─ （后续）保存经鉴权的用户私有覆盖

桌面客户端
├─ 下载并缓存最后一个有效目录版本
├─ 合并本地或用户私有覆盖
├─ 在本机解析并播放用户选择的来源
└─ 不向服务端上传音频、Cookie、临时媒体 URL
```

建议的数据边界：

- `catalog_release`：默认目录的不可变发布版本。
- `albums`、`tracks`：稳定内部 ID 与最小事实字段。
- `default_media_candidates`：`trackId`、Provider、结构化外部引用、来源说明、核验状态和时间。
- `user_catalog_overrides`：用户对默认记录的字段覆盖、隐藏和排序；删除默认记录应保存隐藏标记，不删除全局数据。
- `user_created_albums`、`user_created_tracks`、`user_media_sources`：用户私有新增及其来源选择。

来源解析得到的临时地址、用户登录态和媒体事件 token 均为运行时数据，不进入任何上述持久化模型。

## 5. 实施阶段

### 阶段 A：架构与合规前置

1. 更新版权、架构和产品文档，明确 Bilibili 来源仅在用户本机运行的边界。
2. 审查拟参考的项目与依赖许可证；不得复制不兼容代码。
3. 定义默认来源审核标准、下架处理和用户来源覆盖策略。
4. 确认是否需要跨设备同步；若需要，再单独设计账号、鉴权、隐私、导出和删除机制。

**完成条件**：产品边界、数据责任和测试资源边界获得确认。

### 阶段 B：Electron 桌面壳

1. 建立 `desktop/electron` 分支和独立 worktree。
2. 打包现有 React/Vite 应用，不改变当前 Web MVP 的核心业务规则。
3. 建立主进程、预加载脚本和最小 IPC 白名单；关闭渲染进程的直接原生访问。
4. 验证本地音频选择、现有播放、歌单持久化和生产打包。

**完成条件**：桌面安装包可运行现有 MVP，且不引入未授权的媒体能力。

### 阶段 C：Tauri 学习与技术验证

本阶段可在 Electron 开发期间逐步推进，但不得阻塞 Electron 的可用版本交付。

1. 在需要开始验证时建立 `desktop/tauri` 分支和独立 worktree。
2. 使用现有 React/Vite 构建产物启动 Tauri。
3. 逐步学习并验证最小 Rust command、异步错误处理和受控文件访问。
4. 验证目标平台上的本地文件选择、播放、持久化、构建和调试体验。
5. 记录系统 WebView 差异、打包体积、内存占用和开发维护成本。

**完成条件**：形成可比较的验证报告；本阶段不要求实现完整桌面产品。

### 阶段 D：默认目录后端

1. 定义目录版本与默认来源候选的数据模型和迁移策略。
2. 实现只读默认目录 API、版本号、缓存校验和离线回退。
3. 在客户端实现“默认目录 + 用户本地覆盖”合并，不破坏稳定 ID、歌单或本地音频绑定。
4. 增加管理员维护与发布流程；默认数据必须有来源与审核记录。

**完成条件**：服务不可用时客户端仍能使用上次有效目录与本地能力。

### 阶段 E：桌面端来源 Provider

1. 在 Electron 主线定义平台无关的来源选择规则：本地文件、用户来源、默认来源候选和不可用状态。
2. 实现仅在本机运行的 Provider 适配层；凭据与临时播放地址不离开设备。
3. 增加来源状态、失败提示、用户替换来源和本地文件回退。
4. 为下架、权限不足、过期、网络失败和来源切换补测试。

**完成条件**：可用来源由用户明确选择；失败不会影响目录和歌单，也不会静默规避平台限制。

### 阶段 F：Tauri 进入产品实现的评估决策

在 Electron 主线完成阶段 E 的核心验收后，基于阶段 C 的报告作出一次明确决策：

- 进入 Tauri 产品实现，并按已验证的适配边界逐步复用公共业务逻辑；
- 暂停 Tauri 学习线，继续维护 Electron；或
- 放弃 Tauri 方向并归档结论。

不得在未作出该决策前，将 Tauri 分支扩展为第二套完整产品实现。即使进入产品实现，也必须按单一任务逐步迁移，不能一次性重写 Electron 应用。

## 6. 验收与质量要求

- 每个阶段只完成一个明确任务，核心规则先写成纯函数和测试。
- 涉及桌面端安全边界时，必须进行最小权限、IPC/command 白名单和敏感数据日志检查。
- 涉及默认目录发布时，必须验证稳定 ID、引用完整性、发布回滚和用户覆盖兼容性。
- 不提交真实音乐、歌词、封面、Bilibili 登录态、Cookie、抓取结果、临时播放地址或音频文件。
- Tauri 和 Electron 的公共业务逻辑变更必须先在主线测试通过，再评估是否同步到另一条线。

## 7. 当前阶段与下一步

当前处于**阶段 A：架构与合规前置**。

下一次实现任务应从阶段 A 的单一事项开始：更新项目文档，明确桌面端、后端目录与 Bilibili 本机来源的边界。完成后创建 `desktop/electron`，开始 Electron 桌面壳；`desktop/tauri` 可以稍后在学习和最小验证开始时再创建。
