# MVP 后续工程任务

> 本文以当前仓库代码为基线拆分后续工作。任务按实际剩余风险和产品优先级排序；每个任务原则上只对应一次 Codex 会话。开始任务前应先检查最新 handoff、`git status` 和相关测试，避免重复实现或覆盖已有改动。

## 1. 使用规则

- 一次只领取一个任务；当前任务未通过验收前，不并行实现后续功能。
- “涉及文件”是预计范围。若实现时必须扩大范围，应先说明原因。
- 核心规则优先写成纯函数并补测试，UI 只负责收集输入和展示状态。
- 不提交真实音频、歌词、封面、艺人照片或商业平台抓取内容。
- 不硬编码本地绝对路径、远程 API 地址、播放地址或部署地址。
- 外部元数据和远程音源均不应成为本地 MVP 的启动前提。
- 每个任务完成后至少运行与改动相关的测试；涉及全局状态、存储或构建链路时运行完整检查。

## 2. 当前基线

## 3. P0：补齐专辑目录可维护闭环

### MVP-01：实现用户目录变更的纯领域规则

**任务目标**

定义用户新增和修改专辑、歌曲时使用的数据结构、稳定 ID 规则和纯函数，为 UI 与持久化提供唯一业务入口。

**涉及文件**

- `src/types/catalog.ts`
- `src/features/catalog/catalogMutations.ts`（新增）
- `src/features/catalog/catalogMerge.ts`（新增，若合并逻辑不适合放在 mutations 中）
- `src/tests/catalog.test.ts`

**前置依赖**

- 无。
- 需要保留现有 `CatalogData`、`Album`、`Track` 的稳定 ID 和引用关系。

**实现步骤**

1. 定义带 `schemaVersion` 的用户目录变更结构，至少能表达用户新增记录和字段覆盖；不保存远程原始响应。
2. 实现新增专辑的纯函数，ID 由调用方注入的 ID 工厂生成，避免在测试中依赖随机值。
3. 实现向指定专辑新增歌曲的纯函数，同时维护 `Album.trackIds` 与 `Track.albumId`。
4. 实现默认目录与用户变更的合并函数，禁止直接修改传入对象。
5. 校验标题非空、引用的艺人和专辑存在、ID 不重复。
6. 明确同名专辑和歌曲的策略：MVP 允许同名，但不允许相同 ID。

**验收标准**

- 能向空的用户变更集中新增专辑和歌曲。
- 新歌曲正确引用所属专辑，专辑也包含对应歌曲 ID。
- 合并结果包含内置目录和用户数据，原始内置目录保持不变。
- 修改标题、曲序等字段不会改变实体 ID。
- 无效引用和重复 ID 不会生成损坏的目录。

**测试方式**

- 为新增专辑、新增歌曲、字段覆盖、重复 ID、未知专辑和输入不可变性补单元测试。
- 运行 `npm.cmd run test:run -- src/tests/catalog.test.ts`。
- 运行 `npm.cmd run lint` 和 `npm.cmd run format:check`。

**风险点**

- `Album.trackIds` 与 `Track.albumId` 是双向关系，必须由同一纯函数原子更新。
- 不能用标题、曲序或数组下标生成稳定 ID。
- 不要在本任务中同时实现 UI、存储或远程数据源。

### MVP-02：实现用户目录本地仓储

**任务目标**

为用户新增和修改的目录数据提供可替换的仓储接口，并用浏览器本地存储实现刷新恢复。

**涉及文件**

- `src/features/catalog/localCatalogRepository.ts`（新增）
- `src/infra/storage/localStorageCatalogRepository.ts`（新增）
- `src/tests/catalogStorage.test.ts`（新增）
- `src/types/catalog.ts`（仅在需要导出存储类型时修改）

**前置依赖**

- MVP-01。

**实现步骤**

1. 定义异步仓储接口，至少包含 `load`、`save` 和 `clear`。
2. 使用独立、带版本号的 localStorage key 保存小体积 JSON 元数据；不要与音频 `File` 混存。
3. 读取时校验 JSON 结构和 `schemaVersion`，不直接信任存储内容。
4. 存储为空时返回空的用户变更集。
5. JSON 损坏、版本未知或浏览器拒绝访问时返回明确错误，由上层决定回退。
6. 允许注入 `Storage`，使测试不依赖真实浏览器存储。

**验收标准**

- 保存后可重新读取完全相同的用户目录变更。
- 清除后恢复为空状态，内置目录不受影响。
- 损坏数据不会导致应用启动崩溃，也不会被静默覆盖。
- 存储内容不包含音频、绝对路径、blob URL 或远程播放 URL。

**测试方式**

- 使用内存 `Storage` 替身覆盖保存、读取、清除、损坏 JSON、未知版本和写入异常。
- 运行 `npm.cmd run test:run -- src/tests/catalogStorage.test.ts`。
- 运行 `npm.cmd run lint`、`npm.cmd run format:check` 和 `npm.cmd run build`。

**风险点**

- localStorage 受站点来源、隐私模式和用户清理影响，不能承诺永久保存。
- 必须保留迁移入口，不能把未来结构变化当作普通空数据处理。
- 存储错误时不应覆盖尚可恢复的原始字符串。

### MVP-03：把动态目录接入应用层

**任务目标**

用“内置目录 + 用户变更”生成应用实际使用的目录，消除 `App.tsx` 对固定 `mockCatalog` 的业务依赖。

**涉及文件**

- `src/features/catalog/useCatalogLibrary.ts`（新增）
- `src/app/App.tsx`
- `src/features/catalog/CatalogOverview.tsx`
- `src/tests/app.test.ts`
- `src/tests/catalog.test.ts`

**前置依赖**

- MVP-01。
- MVP-02。

**实现步骤**

1. 实现目录加载 hook，管理 `loading`、`ready`、`error` 和有效 `CatalogData`。
2. 默认立即提供内置目录；本地变更读取成功后再合并，避免空白首屏。
3. 允许向 `App` 注入目录仓储，沿用本地音频仓储的可测试模式。
4. 将加入单曲、加入专辑、队列展示和播放器曲目信息全部改为读取有效目录。
5. 目录存储失败时继续显示内置目录，并给出非阻断中文提示。
6. 处理当前选中专辑在目录更新后不存在的情况，安全回退到第一个可用专辑。

**验收标准**

- 没有本地数据时，现有示例目录和现有功能保持不变。
- 有本地数据时，页面、队列和播放器都能识别新增专辑与歌曲。
- 存储读取失败不会阻止浏览内置目录。
- `App.tsx` 不再用固定目录完成业务查找。

**测试方式**

- 使用内存目录仓储测试空数据、已有数据和加载失败。
- 回归现有 `catalog.test.ts` 与 `app.test.ts`。
- 运行 `npm.cmd run test:run`、`npm.cmd run lint`、`npm.cmd run format:check` 和 `npm.cmd run build`。

**风险点**

- 异步加载期间不能把空目录误保存回本地。
- 目录对象变化可能触发选中专辑或播放器展示重置。
- 不要在本任务中顺便重命名所有 `mockCatalog` 文件或大规模重构目录。

### MVP-04：增加“新增专辑”界面

**任务目标**

让用户无需修改源码即可新增一张专辑，并在刷新后继续看到该专辑。

**涉及文件**

- `src/features/catalog/CatalogOverview.tsx`
- `src/features/catalog/CatalogEditor.tsx`（可新增）
- `src/features/catalog/useCatalogLibrary.ts`
- `src/styles/global.css`
- `src/tests/catalog.test.ts`
- `src/tests/app.test.ts`

**前置依赖**

- MVP-03。

**实现步骤**

1. 在专辑目录区域增加清晰的“新增专辑”入口。
2. 表单收集专辑名和类型；艺人默认使用当前项目艺人，但不把路径或音源写进表单。
3. 提交前 trim 文本并校验必填项。
4. 调用 MVP-01 的纯函数生成专辑并通过仓储保存。
5. 保存成功后选中新专辑；失败时保留用户输入并展示错误。
6. 支持取消，且取消不产生任何数据变更。

**验收标准**

- 用户可以创建空专辑，新专辑立即出现在目录中并被选中。
- 新专辑 ID 稳定且不依赖标题。
- 刷新后新专辑仍存在。
- 空标题不能提交，并显示中文校验信息。
- 新增操作不修改内置示例目录源文件。

**测试方式**

- 组件测试覆盖打开、取消、无效输入、成功提交和保存失败。
- 集成测试覆盖新增后出现在目录以及重新挂载后的恢复。
- 运行 `npm.cmd run test:run`、`npm.cmd run lint`、`npm.cmd run format:check` 和 `npm.cmd run build`。

**风险点**

- 同名专辑可以存在，UI 不应误用标题作为 React key 或实体 ID。
- 表单状态与专辑切换状态不要互相覆盖。
- 不在本任务中实现专辑删除、封面或远程搜索。

### MVP-05：增加“向专辑添加歌曲”界面

**任务目标**

让用户在当前专辑中新增歌曲，并保证曲序、目录引用和刷新恢复正确。

**涉及文件**

- `src/features/catalog/CatalogOverview.tsx`
- `src/features/catalog/CatalogEditor.tsx`（若 MVP-04 已创建）
- `src/features/catalog/useCatalogLibrary.ts`
- `src/styles/global.css`
- `src/tests/catalog.test.ts`
- `src/tests/app.test.ts`

**前置依赖**

- MVP-04。

**实现步骤**

1. 在当前专辑详情中增加“添加歌曲”入口。
2. 表单收集歌曲名和曲序。
3. 艺人和专辑引用来自当前上下文，不允许用户输入任意 ID。
4. 调用纯函数原子新增歌曲并更新专辑 `trackIds`。
5. 列表继续按曲序展示，不依赖写入数组的偶然顺序。
6. 保存失败时不得在内存中留下只有一半引用的歌曲。

**验收标准**

- 新歌曲出现在正确专辑，其他专辑不受影响。
- 专辑 `trackIds` 和歌曲 `albumId` 引用一致。
- 多首新歌按曲序稳定排序。
- 刷新后歌曲仍存在，并可正常加入临时歌单。
- 曲序不是正整数时不能提交。

**测试方式**

- 单元测试覆盖关系更新和排序。
- 组件测试覆盖有效提交、无效曲序、取消和保存失败。
- 集成测试覆盖新增歌曲后加入队列。
- 运行完整 `npm.cmd run test:run`、lint、format check 和 build。

**风险点**

- 同一专辑可能存在重复曲序；MVP 可提示但不要据此生成 ID。
- 写入失败必须保持旧目录完整。
- 不应从文件名自动猜测元数据；批量识别属于后续独立任务。

### MVP-06：支持本地元数据修改与重置

**任务目标**

允许用户修正专辑和歌曲信息，同时保持稳定 ID、队列引用和本地音频绑定不变。

**涉及文件**

- `src/features/catalog/catalogMutations.ts`
- `src/features/catalog/catalogMerge.ts`
- `src/features/catalog/CatalogOverview.tsx`
- `src/features/catalog/CatalogEditor.tsx`
- `src/features/catalog/useCatalogLibrary.ts`
- `src/tests/catalog.test.ts`
- `src/tests/app.test.ts`

**前置依赖**

- MVP-05。

**实现步骤**

1. 实现专辑和歌曲字段 patch 的纯函数，禁止修改 ID 和引用所属实体。
2. 对用户新增记录直接更新本地记录；对内置记录保存用户覆盖字段。
3. 在专辑和歌曲区域提供“编辑”入口，复用新增表单的校验逻辑。
4. 内置记录提供“恢复默认”操作，只清除覆盖字段。
5. 修改标题或曲序后，队列和音频绑定继续通过原 ID 关联。
6. 本任务不实现删除，避免同时引入队列和音频孤儿清理策略。

**验收标准**

- 用户可以修改专辑名、类型及歌曲名、曲序等允许字段。
- 修改前后实体 ID 完全一致。
- 已加入队列或已绑定音频的歌曲修改后仍保持关联。
- 内置记录恢复默认后重新显示内置值。
- 刷新后用户修改仍存在。

**测试方式**

- 单元测试覆盖 patch、重置、禁止修改 ID 和输入不可变性。
- 集成测试覆盖“加入队列/绑定音频后修改标题仍保持关联”。
- 运行完整测试、lint、format check 和 build。

**风险点**

- 不能把完整内置记录复制成覆盖，否则默认目录更新后难以合并。
- 曲序修改会改变展示顺序，但不能改变正在播放 occurrence 的身份。
- 删除和批量修改必须留给后续独立任务。

**任务目标**

**风险点**

- 测试不要依赖随机 UUID；使用可注入 ID 工厂。
- 不要为通过测试而把用户目录重新硬编码进源码。
- 动态目录加载时序可能导致测试误判，应等待 ready 状态。

## 5. P0：完成本地音频真实环境验收

### MVP-08：执行真实浏览器本地音频冒烟测试

**任务目标**

在真实 Chrome 或 Edge 中验证文件选择器、IndexedDB、实际音频解码和播放器状态机的端到端行为。

**涉及文件**

- `docs/testing/local-audio-smoke.md`（新增检查记录）
- 若发现缺陷，仅修改与该缺陷直接相关的 player、local-library、storage 和测试文件。

**前置依赖**

- MVP-07。
- 用户提供或选择仓库外、合法拥有的小型音频文件。

**实现步骤**

1. 启动固定端口的开发服务并记录测试来源地址。
2. 绑定两首歌曲，保留一首未绑定；记录文件格式和浏览器版本。
3. 刷新页面，验证 IndexedDB 绑定与文件名恢复。
4. 验证播放、暂停、上一项、下一项、重复 occurrence 和自然结束。
5. 播放中调整次数、删除当前项和拖拽排序。
6. 验证推进到未绑定歌曲时停住，绑定后可以继续。
7. 验证解绑、重新绑定和同一文件再次选择。
8. 将结果、失败步骤和浏览器差异写入检查记录。

**验收标准**

- Chrome 或 Edge 至少一个当前版本完整通过检查表。
- 刷新后本地绑定恢复，且不会自动播放。
- 未绑定歌曲不会产生网络音源请求或无效播放。
- 队列变化后的实际音频与 occurrence 状态一致。
- 仓库中没有新增任何测试音频或受版权保护资源。

**测试方式**

- 执行人工冒烟检查表。
- 修复缺陷时先补自动化回归测试。
- 最后运行完整 test、lint、format check、build 和 `git diff --check`。

**风险点**

- 自动化测试中的媒体元素和 object URL 是替身，不能代替真实浏览器验收。
- IndexedDB 受协议、域名、端口和隐私模式隔离。
- 文件扩展名通过校验不等于浏览器支持其实际编码。
- 测试音频必须始终位于仓库外。

### MVP-09：防止旧音源的延迟 `ended` 事件推进错误歌曲

**任务目标**

**实现步骤**

**风险点**

- 不要把防竞态逻辑与远程音源 Provider 同时实现。

在用户明确配置并启用时，通过自托管 QQ Music API 服务搜索专辑和歌曲，生成可人工确认的本地导入候选。

**涉及文件**

- `src/infra/catalog/qqMusicCatalogProvider.ts`（新增）
- `src/features/catalog/CatalogImportPanel.tsx`（新增）
- `src/features/catalog/catalogProvider.ts`
- `.env.example`
- `src/tests/catalogProvider.test.ts`
- `README.md`

**前置依赖**

- SOURCE-01。
- 已完成接口稳定性、许可和使用条款评估。

**实现步骤**

1. 从配置读取 API base URL，不提供硬编码公网默认值。
2. 只实现搜索、歌曲详情、歌手专辑和专辑详情所需的最小接口。
3. 校验并标准化响应，设置超时和明确错误。
4. 展示候选和字段差异，用户确认后才写入本地目录。
5. 保存外部引用和必要事实字段，不保存原始响应、Cookie、歌词、封面或评论。
6. 默认关闭 Provider，离线或服务失败时不影响本地功能。

**验收标准**

- 未配置时应用无报错且不发起 QQ API 请求。
- 配置后可搜索并预览候选。
- 只有用户确认的记录才进入本地目录。
- 远程失败、结构变化或空结果有可理解提示。
- 仓库不包含 Cookie、账号信息、音频地址或抓取数据快照。

**测试方式**

- 使用 mock HTTP client 覆盖正常、超时、错误状态、畸形响应和空结果。
- 人工连接本地自托管服务验证一次，不把返回数据提交仓库。
- 运行完整自动化检查和敏感信息扫描。

**风险点**

- 该服务不是 QQ 音乐官方稳定公共 API，接口可能随时变化。
- 代码许可证不等于获得平台数据、图片和音乐内容的使用权。
- 不在本任务中接入 QQ 播放链接。

## 9. P3：播放器体验增强

### PLAYER-01：增加播放进度显示和拖动定位

**任务目标**

显示当前时间、总时长和进度条，并允许用户在当前本地音频内定位。

**涉及文件**

- `src/features/player/PlayerBar.tsx`
- `src/features/player/useLocalAudioPlayback.ts`
- `src/styles/global.css`
- `src/tests/app.test.ts`

**前置依赖**

- MVP-13。

**实现步骤**

1. 监听 `loadedmetadata`、`timeupdate`、`durationchange` 和 seek 相关事件。
2. 将媒体时间作为播放适配层 UI 状态，不写入纯队列领域对象。
3. 增加可访问的 range 控件和中文时间文本。
4. 未加载、时长无效或切源时安全重置。
5. 拖动完成时更新 `audio.currentTime`，不改变 occurrence。

**验收标准**

- 播放时进度和总时长正常更新。
- 用户可以拖动到合法范围内位置。
- 切歌和重新绑定后进度不会沿用旧音源。
- 未绑定歌曲不显示伪造时长。

**测试方式**

- 媒体事件集成测试覆盖加载、更新、seek、切源和无效时长。
- 真实浏览器人工验证。
- 运行完整自动化检查。

**风险点**

- JSDOM 不执行真实媒体时间，需要明确替身行为。
- 部分流媒体源可能不支持任意 seek，未来远程 Provider 需单独声明能力。

### PLAYER-02：增加音量、静音和设置持久化

**任务目标**

提供音量与静音控制，并在刷新后恢复设置但不自动播放。

**涉及文件**

- `src/features/player/PlayerBar.tsx`
- `src/features/player/useLocalAudioPlayback.ts`
- `src/features/player/playerSettingsRepository.ts`（新增）
- `src/infra/storage/localStoragePlayerSettingsRepository.ts`（新增）
- `src/styles/global.css`
- `src/tests/app.test.ts`

**前置依赖**

- PLAYER-01；也可在确认不共享 UI 结构时独立实施。

**实现步骤**

1. 定义带版本号的最小设置结构，只包含音量和静音。
2. 增加 0 至 1 的音量校验与 range 控件。
3. 将设置同步到 `HTMLAudioElement.volume` 和 `muted`。
4. 保存设置并在启动时恢复。
5. 损坏设置回退到安全默认值，不影响队列和音频绑定。

**验收标准**

- 音量和静音即时生效。
- 刷新后设置恢复，播放器仍保持暂停。
- 无效或损坏存储值不会传播到 audio 元素。
- 设置仓储与队列、目录存储彼此独立。

**测试方式**

- 覆盖范围边界、静音切换、刷新恢复和损坏存储。
- 真实浏览器人工听感验证。
- 运行完整自动化检查。

**风险点**

- 静音前音量与静音状态是两个不同概念，恢复时不能互相覆盖。
- 不要持久化 `isPlaying`。
